# Contributing to cfdi4j

Thank you for helping. This guide explains how to build the project, what a good change looks
like, and the rules that keep cfdi4j trustworthy.

## Build

You need JDK 21 or later. Maven is provided by the wrapper:

```sh
./mvnw -B clean verify
```

This compiles every module with Error Prone (`-Werror`), runs the tests, and checks a JaCoCo
coverage minimum of 90 % on `cfdi4j-core`, `cfdi4j-xml`, `cfdi4j-crypto`, `cfdi4j-pagos20` and
`cfdi4j-catalogs`. The build never needs the network once dependencies are downloaded.

Optional profiles:

| Command | What it does |
|---|---|
| `./mvnw -P external-vectors verify` | Also runs tests against third-party vectors that are downloaded at test time and never committed. |
| `./mvnw -P generate-catalogs -pl tools/catalog-generator -am process-classes` | Regenerates catalogs, error matrices and catalog resources from the SAT files. Run `specs/fetch-sources.sh` first. |
| `tools/golden/generate.sh` | Regenerates the golden files with Saxon's command line and OpenSSL. This needs the network. |

## Rules for every change

1. **Public sources only.** Every validation rule, formula or catalog value must come from a
   public SAT document listed in [`specs/SOURCES.md`](specs/SOURCES.md). Cite the document, and the
   page when there is one, in the Javadoc or in the rule's note. Do not implement rules from
   memory, from another product or from private material.
2. **Codes are a contract.** Use an official code (`CFDI40xxx`, `CRP20xxx`) only for the rule that
   implements that matrix entry. Checks of our own use `CFDI4J-xxx`. Never invent official codes.
3. **No silent passes.** A check that needs data cfdi4j does not have (a SAT service, a large
   catalog) reports a *not verified* warning through a port.
4. **Ambiguity goes to an ADR.** When the SAT text allows more than one reading, write down the
   one chosen in [`docs/adr`](docs/adr) and open an issue labeled `spec`.
5. **No personal data.** Tests use only the SAT's public test RFCs and certificates. Never commit
   real RFCs, names, certificates, private keys or passwords.
6. **Generated code is not edited by hand.** Files that start with `// Generated by
   tools/catalog-generator`, and the catalog `.tsv` resources, change only through the
   generator. CI fails if regeneration produces a difference.

## Tests expected with a change

- A new or changed rule needs a valid case and at least one invalid case. The rule tests fail when
  a rule has no invalid case.
- The coverage reports `docs/rules-coverage.md` and `docs/rules-coverage-pagos20.md` are generated.
  After changing rules, regenerate them with `./mvnw verify -Drules.coverage.write=true` and commit
  the result.
- Arithmetic changes need a property-based test (jqwik).
- Anything that changes the XML or the cadena original must keep the golden files passing. The
  expected values of those files are produced without cfdi4j.

## Language

- The domain vocabulary is Spanish and identical to the Anexo 20 and the XML (`Comprobante`,
  `Concepto`, `TasaOCuota`).
- The technical API, Javadoc, commits and ADRs are in English.
- Rule messages are in Spanish in `messages_es.properties`, with English details in
  `messages.properties`.

## Commits and pull requests

- Use [Conventional Commits](https://www.conventionalcommits.org/): `feat(core): …`, `fix(xml): …`,
  `docs: …`, `test: …`, `build: …`.
- Keep commits small and focused, and keep the build green after each one.
- Fill in the pull request template. Mention the SAT source of any rule you add or change.
- Add a line to `CHANGELOG.md` under *Unreleased* for any change users will notice.

## Reporting problems

- Use the issue templates for bugs and feature requests.
- Report security problems privately, as explained in [SECURITY.md](SECURITY.md).

Everyone taking part is expected to follow the [code of conduct](CODE_OF_CONDUCT.md).

## Releasing (maintainers)

1. Set the version without `-SNAPSHOT` in every `pom.xml`:
   `./mvnw versions:set -DnewVersion=X.Y.Z -DgenerateBackupPoms=false`.
2. In `CHANGELOG.md`, rename the section to `## [X.Y.Z] - YYYY-MM-DD`, and commit
   `chore(release): X.Y.Z`.
3. Tag `vX.Y.Z` and push the tag. The [release workflow](.github/workflows/release.yml) does the
   rest:
   - It builds, tests, signs and uploads the bundle to the Central Portal, without publishing it.
   - It creates a draft GitHub release.
4. Review the deployment in the Central Portal and publish it. Then publish the GitHub release.
5. Set the next `-SNAPSHOT` version and open a new *Unreleased* section.
